# ADR-009: процедурный слой движения поверх покадровой анимации

- Статус: Accepted
- Дата: 2026-08-08
- Этап: M7 / post-MVP animation hardening
- Связано: §US-02, §FR-1, §FR-2, §FR-5, §FR-8, §7, §15; [ADR-002](0002-overlay-input-region.md), [ADR-005](0005-pet-pack-sprite-sheet.md)

## Контекст

Pet Pack v1 хранит анимацию как спрайтовый лист: состояние выбирает строку,
диапазон кадров и `frameDurationMs`. После отказа от `AnimatedSprite` кадры
меняются таймером только тогда, когда действительно меняется изображение. На
эталонной системе это снизило CPU в покое с 3.4–4.0% до примерно 0.30%.

Эта модель хорошо подходит для пиксельной покадровой анимации, но смешивает два
разных вида движения:

1. **Изменение позы персонажа** — моргание, взмах лапой, подготовка к прыжку.
   Это содержимое спрайтовых кадров и естественно имеет собственный низкий FPS.
2. **Перемещение целого персонажа** — траектория прыжка, лёгкое покачивание,
   отдача от приземления. Такое движение должно быть плавным относительно
   частоты compositor-а и не требует нового изображения на каждый кадр.

Сейчас второй вид приходится рисовать первым. Встроенный Лайм показывает
последствие: в строке `jumping` фигура уменьшена, чтобы вся траектория прыжка
поместилась в одну ячейку. На экране это читается как изменение размера
питомца. Исправление только ассетом либо требует большого прозрачного canvas,
либо сохраняет ту же ошибку масштаба.

Увеличение числа спрайтовых кадров до 60–120 FPS проблему не решает: растут
размер Pet Pack, текстура и число перерисовок, хотя значительная часть кадров
отличается только положением одной и той же фигуры.

При этом у motion есть два ограничения существующего overlay, которые нельзя
оставить деталями реализации.

### Поверхность имеет конечную геометрию

Текущее окно построено плотно вокруг питомца и пузыря. При ячейке 192×208 окно
примерно 192×284: сверху есть место под пузырь, но по бокам и снизу свободного
пространства нет. Translation не может переместить QML-элемент за границы
поверхности: он будет обрезан.

Значит, motion требует заранее решить, откуда берётся место для траектории.
Растягивать layer-shell поверхность на каждый прыжок нежелательно: по опыту
перетаскивания изменение геометрии поверхности — отдельная дорогая операция, а
motion возникает значительно чаще drag.

### Input region обязан двигаться вместе с визуалом

ADR-002 принял input region, вычисленный по альфа-каналу один раз на анимацию и
кэшируемый. Покадровый пересчёт был измерен и отвергнут: 10.8 мс на кадр и
19–22% CPU при ~90 Гц.

Если визуал сдвинуть procedural motion на 24 px, а маску оставить на месте,
кликабельная область перестанет совпадать с питомцем: в старом месте останется
невидимая зона ввода, а в новом видимые пиксели перестанут принимать клики.
Такое поведение нарушает решение ADR-002 и §FR-2.

При этом для translation не требуется заново читать альфа-канал. Уже
вычисленный `QRegion` можно перенести на тот же pixel-snapped offset. Цена измерена: `QRegion::translated()` вместе с `setMask` стоит 0.013–0.041 мс
на вызов при 37–75 прямоугольниках, то есть 0.1–0.4% ядра при 90 Гц — против
10.8 мс и 19–22% у пересчёта по альфе. Разница от 250 до 800 раз, замер
и оговорка записаны в [ADR-002](0002-overlay-input-region.md).

Оговорка существенна: замерена клиентская сторона. Запросы Wayland
буферизуются до commit, поэтому цена у композитора при одном переносе
на кадр этим не доказана и остаётся в открытых вопросах.

ADR-005 уже требует отделять способ отрисовки от поведения и оставляет
возможность второго renderer-а. Процедурное движение не является новым
renderer-ом: оно должно одинаково накладываться на текущий `sprite-sheet` и на
будущий Rive/Lottie renderer, если такой появится.

## Рассматриваемые варианты

### Вариант A — всё движение остаётся внутри спрайтов

Прыжки, покачивания и другие перемещения рисуются отдельными кадрами в общей
ячейке.

Плюсы:

- текущий runtime не меняется;
- Pet Pack остаётся максимально простым;
- результат полностью контролирует художник;
- геометрия поверхности и input region уже соответствуют кадрам.

Минусы:

- траектория требует большого прозрачного canvas или изменения масштаба фигуры;
- плавное движение требует десятков почти одинаковых кадров;
- размер текстуры и стоимость redraw растут вместе с желаемой плавностью;
- генератору Pet Pack сложнее удерживать одинаковый размер и anchor фигуры;
- проблема встроенного `jumping` остаётся свойством формата.

### Вариант B — постоянно рендерить всю сцену в 60/90/120 FPS

Спрайт остаётся покадровым, но QML-сцена всегда обновляется с частотой экрана,
а положение вычисляется runtime-ом.

Плюсы:

- движение может быть плавным;
- реализация motion не зависит от FPS sprite animation.

Минусы:

- возвращает уже измеренную проблему `AnimatedSprite`: питомец тратит кадры
  compositor-а даже когда неподвижен;
- нарушает достигнутую цель CPU в idle;
- не решает вопрос границ поверхности и input region.

### Вариант C — событийный procedural motion layer поверх renderer-а

Спрайтовая анимация продолжает менять изображение с собственным темпом.
Отдельный слой translation активируется только на время движения и на каждом
frame callback compositor-а вычисляет положение визуала. Когда motion закончен,
непрерывных QML-анимаций нет и сцена снова обновляется только при смене
спрайтового кадра.

Для пакета, содержащего motion, при загрузке вычисляется ограничивающий
**motion envelope** — максимальные отрицательные и положительные смещения по X/Y
всех допустимых keyframes. Поверхность получает этот резерв один раз и не
меняет размер на каждом движении.

Кэшированный input region текущей анимации переносится на фактический motion
offset; альфа-канал при этом не анализируется заново.

Плюсы:

- плавность перемещения не требует дополнительных sprite frames;
- idle сохраняет текущую модель потребления CPU;
- размер и anchor фигуры можно держать постоянными между кадрами;
- геометрия поверхности стабильна во время motion;
- движение становится декларативной частью Pet Pack;
- слой применим к будущему renderer-у и не конкурирует с `renderer` из ADR-005.

Минусы:

- появляется второй временной контур: sprite clock и motion clock;
- поверхность Pet Pack с motion постоянно больше плотной рамки питомца;
- размер резерва влияет на память/композитинг и потому требует жёстких лимитов;
- input mask приходится обновлять с частотой motion, хотя без альфа-пересчёта;
- обновление маски идёт с частотой motion — измерено, 0.013–0.041 мс
  на вызов, то есть 0.1–0.4% ядра при 90 Гц (см. ADR-002);
- расширяется Pet Pack manifest и host↔core контракт.

### Вариант D — растягивать поверхность только на время motion

Перед началом движения окно увеличивается до нужной траектории, после завершения
сжимается обратно — аналогично механике drag из ADR-002.

Плюсы:

- в покое поверхность остаётся минимальной;
- размер резерва не платится постоянно.

Минусы:

- изменение layer-shell геометрии становится частью каждой реакции;
- возможны гонки между resize, compositor configure и первым кадром движения;
- motion заметно чаще drag, поэтому временная цена из сценария
  перетаскивания превращается в штатную;
- смена реакции посреди движения усложняет возврат геометрии.

### Вариант E — сразу перейти на Rive/Lottie

Пиксельного питомца заменить векторным/скелетным renderer-ом, где движение и
интерполяция являются частью формата.

Плюсы:

- профессиональная временная шкала и интерполяция;
- меньше собственной логики motion.

Минусы:

- не решает задачу существующих pixel-art Pet Pack;
- существенно расширяет runtime, зависимости и поверхность валидатора;
- это второй renderer из ADR-005, а не улучшение текущего;
- несоразмерно одной измеренной проблеме прыжка.

## Критерии выбора

1. В покое питомец не должен снова перерисовываться с частотой дисплея.
2. Плавность перемещения не должна требовать 60 уникальных изображений в секунду.
3. Pixel art остаётся резким при fractional scaling Plasma.
4. Существующие Pet Pack v1 продолжают работать без изменений.
5. Behavior core выбирает смысл реакции, но не содержит QML-специфичных деталей.
6. Motion не должен препятствовать появлению второго renderer-а из ADR-005.
7. Более приоритетная реакция должна уметь безопасно прервать текущее движение.
8. Ни один допустимый motion не должен обрезаться границами поверхности.
9. Геометрия layer-shell поверхности не должна меняться на каждом motion.
10. Input region должен совпадать с фактическим положением питомца без
    покадрового анализа альфа-канала.
11. Стоимость активного motion, включая обновление input region, должна быть
    измерена до принятия решения.

## Решение

Предлагается **вариант C: событийный procedural motion layer с постоянным
bounded motion envelope**.

ADR остаётся `Proposed`, пока не измерена стоимость обновления уже готового
input region на активном motion. Если этот путь не укладывается в приемлемый
CPU-бюджет, решение пересматривается до `Accepted`, а не маскируется stale
регионом или отключением интерактивности.

### Два независимых временных контура

Renderer отвечает за изменение изображения:

```text
sprite frames:  6–24 FPS  ──► pose
```

Motion layer отвечает только за трансформацию уже выбранного визуала:

```text
frame callback: 60/90/120 Hz ──► translation
```

Итоговый кадр — композиция этих двух результатов. Непрерывный frame callback
нужен только пока активен motion. После его завершения слой становится
тождественным, и текущая оптимизация `Pet.qml` сохраняется.

### Первая версия motion ограничена translation

Для `sprite-sheet` в первой реализации допускается только перемещение `x/y`.
`scale` и произвольный `rotation` не входят в контракт: оба требуют
передискретизации pixel art и возвращают визуальную проблему, которую решение
как раз должно устранить.

Это достаточно для исходной задачи: прыжок рисуется как несколько поз одного
масштаба, а высота задаётся motion layer.

### Геометрия поверхности: резерв вычисляется при загрузке Pet Pack

Host вычисляет минимальный прямоугольник, в котором помещается базовая область
питомца при любом объявленном translation:

```text
reserve.left   = max(0, -minX)
reserve.right  = max(0,  maxX)
reserve.top    = max(0, -minY)
reserve.bottom = max(0,  maxY)
```

Геометрия overlay для пакета строится как:

```text
motion reserve
+ базовая область питомца
+ отдельный reserve пузыря
```

Резерв пузыря и резерв motion не считаются взаимозаменяемыми. Пузырь может быть
скрыт в момент движения, поэтому `y: -24` не имеет права использовать место,
которое существует только пока показана реплика.

Размер поверхности меняется при загрузке/смене Pet Pack или при изменении
масштаба/DPR, но **не на старте и конце каждого motion**. Пакет без `motion`
получает нулевой reserve и сохраняет текущую плотную геометрию.

Чтобы недоверенный manifest не превратил небольшого питомца в огромную
прозрачную layer-shell поверхность, validator ограничивает абсолютный motion
envelope. Конкретный предел должен быть выбран по измерениям и зафиксирован в
schema/validator до реализации; превышение — ошибка импорта, не clamp в runtime.

### Input region: перенос готовой маски, не пересчёт альфы

Для текущей анимации сохраняется кэшированный базовый `QRegion`, вычисленный по
ADR-002. На каждом изменении pixel-snapped motion offset host получает:

```text
petRegion = cachedAnimationRegion.translated(dx, dy)
inputRegion = petRegion | bubbleRegion
window.setMask(inputRegion)
```

Координаты region и визуала обязаны проходить через один и тот же snapping:
разные округления снова разнесут видимую и кликабельную области.

Важно различать две стоимости:

- **запрещено:** заново читать/анализировать альфа-канал на каждом кадре — это
  вариант C из ADR-002 с измеренными 19–22% CPU;
- **предлагается и требует замера:** перенести уже готовые ~десятки
  прямоугольников и передать новую маску композитору.

Если offset после snapping не изменился, `setMask` не вызывается. Это особенно
важно на fractional scaling: несколько соседних временных отсчётов могут
попасть в один физический пиксель.

Stale region не является допустимой деградацией: если обновление маски окажется
слишком дорогим, motion в таком виде не принимается. Делать питомца визуально
подвижным, но кликабельным в старом месте хуже отсутствия motion.

### Координаты и pixel snapping

Motion задаётся в логических пикселях Pet Pack, относительно нейтрального anchor
питомца. Перед применением translation host привязывает координату к сетке
физических пикселей текущего экрана:

```text
physical = round(logical * devicePixelRatio)
logical' = physical / devicePixelRatio
```

Тот же `logical'` используется и для visual transform, и для переноса input
region.

### Декларативный контракт

Motion является необязательной частью анимации. Отсутствие поля означает
тождественное преобразование и сохраняет поведение всех существующих пакетов.

Предлагаемый минимальный вид манифеста:

```json
{
  "animations": {
    "charging": {
      "row": 2,
      "startColumn": 0,
      "frames": 5,
      "frameDurationMs": 120,
      "motion": {
        "durationMs": 600,
        "loop": true,
        "keyframes": [
          { "at": 0.0, "x": 0, "y": 0, "easing": "out-quad" },
          { "at": 0.5, "x": 0, "y": -24, "easing": "in-out-quad" },
          { "at": 1.0, "x": 0, "y": 0, "easing": "in-quad" }
        ]
      }
    }
  }
}
```

`at` лежит в диапазоне `0.0..1.0`. Набор easing фиксирован схемой, а не
передаётся как код или выражение. Pet Pack остаётся чистыми данными.

Поле добавляется в текущую schema как **optional additive extension**. Номер
`schemaVersion` не повышается, пока семантика существующих полей не меняется и
старые пакеты остаются валидными. Если реализация покажет, что это невозможно
обеспечить текущим JSON Schema/validator контрактом, повышение версии выносится
в отдельное решение до публикации поддержки motion.

### Граница core и host

Core:

- разбирает и валидирует недоверенное описание motion вместе с manifest;
- проверяет лимиты, диапазоны, порядок keyframes и допустимые easing;
- вычисляет либо позволяет host вычислить bounded envelope из уже проверенных
  координат;
- отдаёт host-у нормализованные данные, без QML/Qt типов.

Host/QML:

- резервирует место под motion при конфигурации поверхности;
- интерполирует translation по времени;
- делает pixel snapping с учётом DPR текущего экрана;
- применяет тот же offset к кэшированному input region;
- включает непрерывное обновление только на время motion;
- останавливает motion при скрытии/блокировке и при `reduced motion`.

Behavior core не вычисляет координаты и не знает частоту compositor-а.
`Reaction.animation` по-прежнему выбирает анимацию; motion является свойством
этой анимации в активном Pet Pack.

### Прерывание

Если новая реакция с более высоким приоритетом меняет анимацию, текущий motion
немедленно отменяется и новая анимация начинается из своей нейтральной точки.
В том же update input region переносится в новую позицию; не допускается кадр,
в котором visual уже вернулся, а mask ещё осталась на старом offset.

Перенос остаточной скорости между состояниями не делается в первой версии:
предсказуемый snap к anchor предпочтительнее скрытой физической модели.

`reduced motion` отключает procedural motion полностью, но sprite animation
сохраняет уже существующее поведение reduced-motion режима. В этом режиме
motion reserve может оставаться в геометрии поверхности: изменение размера
окна при переключении accessibility-настройки не окупает небольшой постоянный
резерв и усложняет позиционирование.

## Последствия

- Встроенную строку `jumping` можно перерисовать с постоянным размером фигуры:
  sprite frames будут описывать позу, motion — высоту.
- Pet Pack validator получает проверки `durationMs`, числа keyframes, диапазона
  `at`, координат, envelope и списка easing. Должны быть жёсткие верхние лимиты.
- Pet Pack с motion имеет немного большую overlay-поверхность даже в покое;
  пакет без motion не платит эту цену.
- Резерв под пузырь не может использоваться как резерв motion.
- Host↔core ABI получает нормализованный motion DTO. QML не разбирает JSON.
- `Pet.qml` получает внешний transform-контейнер; текущая логика смещения atlas
  и sprite timer не меняется.
- Input-region cache из ADR-002 сохраняется: дорогого альфа-пересчёта на кадр
  нет. На активном motion меняется только положение готового региона.
- Perf-тест должен отдельно измерять idle без motion, idle пакета с reserve и
  активный motion вместе с `setMask`. Цель `CPU ≤ 2% idle` не оправдывает
  постоянный render loop, но для активного motion нужна отдельная измеренная
  граница.
- Skill генерации Pet Pack из §15 получает возможность разделять pose frames и
  trajectory вместо уменьшения персонажа ради canvas.
- Новый renderer (например Rive) может использовать тот же внешний motion либо
  объявить, что конкретная анимация уже содержит движение внутри себя; этот
  вопрос решается при добавлении второго renderer-а.

## Проверка перед переводом в Accepted

ADR нельзя переводить из `Proposed` в `Accepted`, пока на эталонной системе не
сделан spike минимум для DPR 1.0 и текущего fractional DPR с частотами экрана,
доступными на машине.

Нужно сравнить:

1. baseline без motion;
2. visual translation без изменения mask — только как контроль цены render;
3. visual translation + `cachedRegion.translated()` + `setMask()` при каждом
   изменившемся pixel-snapped offset.

Измеряются CPU, число фактических `setMask`, frame pacing и отсутствие
рассинхронизации visual/input. Отдельно проверяется, что motion у краёв envelope
не обрезается и что прозрачный reserve не создаёт кликабельной мёртвой зоны.

Если обновление region даёт неприемлемую цену, рассматриваются альтернативы до
принятия ADR: более низкая частота motion, обновление mask только при изменении
физического пикселя, либо отказ от procedural translation для интерактивного
sprite renderer. Покадровый альфа-пересчёт из ADR-002 не возвращается.

## Открытые вопросы

1. Нужны ли в первой реализации произвольные keyframes или достаточно небольшого
   набора presets (`jump`, `bob`, `shake`). Решение можно принять на реализации,
   если внешний контракт остаётся декларативным и совместимым.
2. Какой максимальный motion envelope допустим по памяти, композитингу и UX.
   Предел должен появиться до поддержки импорта таких пакетов.
3. Нужна ли синхронизация ключевой точки motion с конкретным sprite frame
   (например, apex прыжка с позой в воздухе). Не включать до появления реального
   ассета, которому это требуется.
4. После принятия ADR следует обновить §FR-1/§FR-2/§FR-8/§15 спецификации
   отдельной правкой с повышением версии документа, как требует `AGENTS.md`.
