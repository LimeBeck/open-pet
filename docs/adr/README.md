технологий, модель интеграции с платформой, формат контрактов.

ADR-001…004 заданы §16 спецификации как выход этапа M0. ADR-001 и ADR-002
закрыты спайками из [`spikes/`](../../spikes/README.md).

ADR-003 и ADR-004 перенесены в M4: они описывают источники событий — активное
приложение и уведомления, — а не риски overlay и FFI, ради снятия которых
затевался M0. До своих проб они содержат контекст, варианты и критерии выбора.

## Процесс

1. Копируешь [`template.md`](template.md) в `NNNN-краткое-имя.md`, номер — следующий
   свободный, четыре цифры.
2. Заводишь со статусом `Proposed`. Описываешь контекст и варианты честно:
   ADR ценен тем, что сохраняет отвергнутые альтернативы и причину отказа.
3. После решения — `Accepted`, дата, раздел «Последствия».
4. Решение перестало действовать — не переписываешь старый ADR, а заводишь новый
   и ставишь старому `Superseded by ADR-NNNN`.
5. Индекс выше обновляется в том же изменении, что и сам ADR.

## Статусы

| Статус | Значение |
|---|---|
| `Proposed` | Вопрос сформулирован, решение не принято |
| `Accepted` | Решение принято и действует |
| `Superseded by ADR-NNNN` | Заменено более поздним решением |
| `Rejected` | Вариант рассматривался и отклонён; запись оставлена ради причины |

## Что заслуживает ADR

Заслуживает: выбор FFI, формат Pet Pack, модель установки платформенных
интеграций, отказ от источника событий, расширение границ MVP из §4.3.

Не заслуживает: выбор имени функции, структура одного модуля, форматирование,
любое решение, которое дёшево переиграть.
