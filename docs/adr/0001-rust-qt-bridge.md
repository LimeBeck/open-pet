# ADR-001: способ Rust↔Qt bridge

- Статус: Accepted
- Дата: 2026-08-06
- Этап: M0
- Связано: §8 (архитектура), §14 (риск «FFI Qt/Rust замедляет разработку»), §16

## Контекст

Ядро домена — Rust: state machine, шаблоны фраз, LLM gateway, валидация Pet Pack,
модель конфигурации. Хост — C++ поверх Qt 6 / KF6: LayerShellQt, tray, KIdleTime,
D-Bus-адаптеры. Через границу ходят нормализованные DTO (§FR-4) и `Reaction` (§FR-5),
а также команды в обратную сторону.

Требования, которые давят на выбор:

- через границу не должны просачиваться Qt-типы — иначе core перестанет быть
  переносимым на Windows/macOS адаптеры (гипотеза 4 из §1);
- граница должна пережить смену binding-фреймворка без переписывания core;
- поток событий асинхронный: адаптеры публикуют события, core отвечает реакциями,
  UI обновляется в Qt-потоке.

Спецификация в §8 уже выражает предпочтение: статическая Rust-библиотека с узким
C ABI и безопасной C++-обёрткой. Этот ADR должен его подтвердить или опровергнуть
по результатам spike, а не принять на веру.

## Рассматриваемые варианты

### Вариант A — статическая Rust-библиотека, узкий C ABI, C++-обёртка

Заголовки генерируются (например, cbindgen), сборка связывается через CMake +
Corrosion. Минимальная связанность с экосистемой биндингов, предсказуемая ABI.
Цена: DTO приходится описывать вручную по обе стороны, `Option`/`enum` с полями
разворачиваются в плоские C-структуры, вся асинхронность и владение памятью —
ручные.

### Вариант B — cxx / cxx-qt

Генерация безопасного моста по декларации, готовая интеграция с сигналами
и типами Qt, меньше ручного кода на DTO. Цена: связанность с версиями
фреймворка и его моделью сборки; вопрос, насколько чисто через него проходит
граница «без Qt-типов в core».

### Вариант C — оставить оркестрацию в C++, Rust только как чистые функции

Наименьший риск на старте: state machine вызывается синхронно, состояние живёт
в хосте. Цена — ядро перестаёт быть ядром, и часть логики придётся переносить
при добавлении второй платформы. Спецификация допускает это как временную меру (§14).

## Критерии выбора

- Сквозной проход события: адаптер → core → `Reaction` → QML, без Qt-типов в core.
- Стоимость добавления одного нового варианта `DesktopEvent` — в строках и файлах.
- Поведение при панике в Rust: паника не должна разрушать процесс хоста.
- Воспроизводимость сборки на эталонной системе и в CI, время холодной сборки.
- Сколько кода придётся выбросить при смене подхода.

## Результаты спайка

Реализация и замеры — [`spikes/02-rust-bridge/`](../../spikes/02-rust-bridge/README.md).
Проверялся вариант A; варианты B и C не измерялись (см. «Открытые вопросы»).

| Критерий | Результат |
|---|---|
| Сквозной проход события без Qt-типов в core | Проходит. `behavior.rs` не знает ни о C, ни о Qt, покрыт собственными тестами |
| Цена нового варианта `DesktopEvent` | 48 строк в 5 файлах, из них 20 — механический шаблон обёртки |
| Паника в Rust | `catch_unwind` на каждой границе; процесс жив, ядро продолжает отвечать |
| Асинхронность | Callback из потока ядра + `QMetaObject::invokeMethod(Qt::QueuedConnection)`; подтверждено сравнением `QThread::currentThread()` |
| Сборка | Холодная 3.95 с, правка домена 0.59 с; один `add_custom_command` с `cargo` |
| Цена смены подхода | Выбрасывается только `lib.rs` и `corebridge.cpp`; домен и хост не затрагиваются |

## Решение

Принят **вариант A**: статическая Rust-библиотека, узкий C ABI, написанный
руками заголовок, безопасная C++-обёртка.

Основание — не производительность, а изоляция. Домен не сделал ни одной уступки
ради FFI, а при смене моста выбрасываются два файла из шести. Интеграция сборки
обошлась в один custom command, то есть опасение из §14 о том, что FFI замедлит
разработку, на этом объёме не подтвердилось.

Правила границы, зафиксированные спайком:

1. Через границу ходят только POD-типы. Никаких Qt-типов, никакого владения
   памятью, пересекающего границу.
2. Событие — плоская структура, а не размеченное объединение. Поля, не
   относящиеся к текущему `kind`, игнорируются; хост обязан обнулять структуру.
3. Строки наружу — фиксированный буфер, внутрь — указатель с длиной, валидный
   только на время вызова.
4. Каждая функция `extern "C"` оборачивается в `catch_unwind`. Паника
   не пересекает границу никогда.
5. `panic = "abort"` в профиле release запрещён: он убил бы `catch_unwind`
   и вместе с ним процесс хоста.
6. Заголовок пишется руками, а не генерируется: он и есть контракт, и его
   изменения должны быть заметны на ревью.
7. Изменение раскладки любой структуры границы поднимает `OPENPET_ABI_VERSION`;
   хост сверяет версию при создании моста и отказывается работать при расхождении.

## Последствия

- `core/` — Rust-крейт без зависимостей; ни сборка, ни тесты не требуют сети.
  Это условие для CI, а не удобство. **Уточнено в M5:** правило ослаблено
  для разбора недоверенного ввода — см. [ADR-007](0007-untrusted-json-parsing.md).
- `platform/contracts/` содержит C-заголовок и его Rust-зеркало. Они правятся
  синхронно, расхождение ловится версией ABI, а не отладчиком.
- Оркестрация живёт в Rust, а не в C++: вариант C из §14 как временная мера
  не понадобился.
- Обёртка на 20 строк на событие терпима при восьми событиях §FR-4. Если их
  станет заметно больше, потребуется генерация — но не раньше.
- Нужен собственный хук паники: стандартный печатает сообщение в stderr,
  а оно должно уходить в диагностический журнал и не содержать пользовательского
  содержимого (§9).

## Открытые вопросы

- Варианты B (cxx-qt) и C не измерялись. Пересматривать решение имеет смысл,
  только если шаблонный код обёртки начнёт мешать.
- Стоимость границы на потоке событий не проверялась: в спайке события подавались
  единицами. Замер — в M3, когда появятся настоящие адаптеры.
- Путь реакции до QML не пройден: спайк доводит её до C++. Закрывается в M1.
- Где живёт состояние питомца — в core или дублируется во ViewModel? Спайк держит
  его в core; на UI это ещё не проверялось.
