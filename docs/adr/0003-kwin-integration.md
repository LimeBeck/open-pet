# ADR-003: модель KWin integration и её установка

- Статус: Accepted
- Дата: 2026-08-07
- Этап: M4
- Связано: §FR-3, §4.2, §US-05, §10, §14 (риск «активное приложение недоступно клиенту»)

## Контекст

Событие `ActiveAppChanged { app_id }` (§FR-4) требует знать, какое приложение
сейчас активно. Под Wayland обычный клиент не наблюдает чужие окна — это позиция
модели безопасности протокола, а не пробел в реализации. Значит, источник должен
жить внутри композитора.

Спецификация уже ограничивает решение (§FR-3): отдельный, **явно устанавливаемый**
пользователем KWin script/plugin с минимальным payload. Наружу отдаётся только
нормализованный app id и факт смены — без заголовков окон и содержимого (§4.2).

Отсюда два вопроса, а не один: чем технически является интеграция и как она
попадает в систему пользователя, не превращая установку приложения в квест.

## Рассматриваемые варианты

### Вариант A — KWin script (JS) + собственный D-Bus-сервис приложения

Скрипт подписывается на смену активного окна и вызывает метод нашего сервиса,
передавая только app id. Не требует компиляции под версию KWin, ставится в
пользовательский каталог, снимается так же просто. Цена: зависимость от
стабильности scripting API между версиями Plasma; отдельный шаг установки в UI.

### Вариант B — KWin plugin/effect на C++

Больше возможностей и меньше слоёв. Цена: сборка под конкретную версию KWin,
установка в системные каталоги, обновление ломается при апдейте Plasma.
Для минимального payload это заметный перебор.

### Вариант C — переносимый источник вместо KWin-специфичного

Проверить, даёт ли какой-либо портал или общий интерфейс нужный минимум
переносимо. Если да — выиграем на будущих композиторах; если нет — отклонить
явно и записать причину, чтобы к вопросу не возвращались.

### Вариант D — не поддерживать в MVP

`ActiveAppChanged` помечается `unsupported`, правила `busy`/`curious` работают
от других сигналов. Спецификация это допускает (§10): интеграция не установлена —
capability недоступна, приложение работает. Цена: US-05 остаётся непроверенным.

## Критерии выбора

- Payload ограничен app id и фактом смены; заголовки окон не пересекают границу.
- Установка и удаление выполняются пользователем осознанно и обратимо.
- Отсутствие интеграции не ломает ничего, кроме одной capability.
- Совместимость с Plasma 6.2+ без пересборки под каждую минорную версию.
- Понятная диагностика: UI показывает, установлена интеграция или нет, и почему.

## Решение

Принят **вариант A**: KWin-скрипт на JavaScript плюс собственный сервис D-Bus
на стороне приложения.

Скрипт подписывается на `workspace.windowActivated` и вызывает метод
`SetActiveApp` нашего сервиса, передавая только `resourceClass` — идентификатор
вида `org.kde.konsole`. Заголовок окна, геометрия, идентификатор окна и pid
не передаются, и добавлять их в скрипт нельзя: в заголовке имя открытого
документа, что прямо запрещено §4.2.

Вариант B (плагин на C++) отклонён: сборка под конкретную версию KWin
и установка в системные каталоги — несоразмерная цена за передачу одной
строки. Вариант C (переносимый источник) отклонён за отсутствием такового:
портала, отдающего активное приложение, в системе нет.

Границы, зафиксированные реализацией:

1. Скрипт игнорирует служебные поверхности рабочего стола — панели,
   всплывающие подсказки, уведомления и OSD. Иначе питомец реагировал бы
   на собственный пузырь с репликой.
2. Скрипт игнорирует само приложение: реакция на себя выглядела бы
   как разговор с зеркалом.
3. Приёмная сторона ограничивает длину строки: сюда приходит идентификатор
   приложения, а не текст.
4. Идентификатор не пишется в журнал. Сам по себе он безобиден, но
   последовательность таких записей — это история приложений пользователя,
   а её §9 хранить запрещает.

## Что проверено

Сквозной путь работает на живой Plasma 6.7.4: переключение окна →
`workspace.windowActivated` в скрипте → вызов D-Bus → адаптер → ядро →
состояние `curious` с репликой.

Пока скрипт не установлен, capability источника — `permission_required`,
а не `unsupported`: нужно осознанное действие пользователя, а не исправление
ошибки.

### Установка оказалась сложнее, чем «скопировать каталог»

Две ловушки, каждая стоила отдельной проверки.

**`X-Plasma-API: declarativescript` в метаданных ломает загрузку.** Этот ключ
предназначен для скриптов на QML в `contents/ui/`. У обычного JS-скрипта
в `contents/code/main.js` его быть не должно — с ним KWin пакет не принимает.

**Свежеустановленный скрипт не поднимается до перезапуска KWin.** Ни
`reconfigure`, ни `start()` его не подхватывают: KWin сканирует пакеты
скриптов при старте, и по имени новый пакет ещё не известен. Проверено
и с копированием каталога вручную, и со штатным `kpackagetool6` — результат
одинаковый.

Обход для текущей сессии есть: `loadScript` с **полным путём** к файлу минует
реестр пакетов и работает сразу. То есть приложение может после установки
активировать скрипт само, не требуя перезахода.

## Последствия

- Установка скрипта — отдельное действие пользователя. Приложение кладёт
  файлы в общий каталог данных, но не трогает `kwinrc` само: включение
  скрипта меняет конфигурацию рабочего стола, и делать это молча нельзя.
- Удобный интерфейс установки — работа M7. Он обязан либо активировать скрипт
  через `loadScript` по пути, либо честно сказать пользователю, что до перезахода
  в сессию источник не заработает. Молча оставить неработающую capability нельзя.
- Установка выполняется через `kpackagetool6 --type KWin/Script --install`,
  а не копированием каталога: так пакет попадает в реестр и будет виден
  после следующего входа в сессию.
- Скрипт зависит от стабильности `workspace.windowActivated` между версиями
  Plasma. Матрица совместимости пополняется по мере проверки.

## Открытые вопросы

- Признаки служебных поверхностей в скрипте (`dock`, `popupWindow`,
  `notification` и прочие) отработали без ложных срабатываний за короткую
  проверку, но длительного наблюдения не было: панель и собственный пузырь
  питомца активацию не вызывали.
- Как приложение узнаёт версию установленной интеграции и что делает
  при несовместимости — `degraded` или `unsupported`?
- Debounce на стороне скрипта пока не сделан: быстрый alt-tab даёт поток
  вызовов D-Bus, который гасится уже в ядре по cooldown. Гасить раньше
  дешевле, но сначала нужно измерить, есть ли проблема.
- Как удалять скрипт при удалении приложения?
