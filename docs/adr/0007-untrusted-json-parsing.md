# ADR-007: разбор недоверенного JSON — зависимость против своего парсера

- Статус: Accepted
- Дата: 2026-08-07
- Этап: M5
- Связано: [ADR-001](0001-rust-qt-bridge.md), [ADR-005](0005-pet-pack-sprite-sheet.md), §FR-8, §8

## Контекст

[ADR-001](0001-rust-qt-bridge.md) зафиксировал в последствиях: «`core/` —
Rust-крейт без зависимостей; ни сборка, ни тесты не требуют сети. Это условие
для CI, а не удобство». На тот момент ядру нечего было разбирать: события
приходили плоскими структурами через C ABI.

M5 меняет исходные данные. Валидатор Pet Pack разбирает `manifest.json`
из пакета, который пользователь взял неизвестно где. Это недоверенный ввод
в самом прямом смысле, и §FR-8 делает валидатор границей безопасности:
path traversal, zip-бомбы, лимиты размеров.

Правило «без зависимостей» и требование безопасного разбора недоверенного
ввода вошли в противоречие. Одно из них надо ослабить осознанно.

## Рассматриваемые варианты

### Вариант A — свой парсер JSON в ядре

Сохраняет правило дословно. Цена: разбор недоверенного ввода собственным
парсером — классический источник уязвимостей. Глубокая вложенность, длинные
числа, экранирование, суррогатные пары UTF-16, повторяющиеся ключи — каждая
из этих мелочей уже становилась чьей-то CVE. Писать это ради того, чтобы
не добавлять зависимость, значит менять понятный риск на непонятный.

### Вариант B — `serde_json`

Одна широко используемая и разобранная библиотека вместо своего кода.
Цена: сборка ядра начинает требовать сети или заранее выкачанных исходников;
следствие ADR-001 перестаёт быть верным дословно.

### Вариант C — разбирать JSON в хосте через `QJsonDocument`

Парсер тоже проверенный, зависимость уже есть. Цена: граница безопасности
переезжает из ядра в C++. §8 прямо относит валидацию Pet Pack к Rust Core,
и разносить проверку по двум языкам — верный способ получить расхождение
между тем, что проверено, и тем, что использовано.

## Критерии выбора

- Недоверенный ввод разбирается кодом, который уже пережил чужие атаки,
  а не написан по случаю.
- Граница безопасности остаётся в одном месте и на одном языке.
- Сборка воспроизводима: одинаковый результат на машине разработчика и в CI.

## Решение

Принят **вариант B**: ядро получает `serde` и `serde_json`.

Правило ADR-001 переформулируется, а не отменяется:

> Ядро не тянет зависимости ради удобства. Исключение — разбор недоверенного
> ввода: там своя реализация опаснее чужой проверенной.

Каждое новое исключение обосновывается отдельно и записывается сюда.

Воспроизводимость обеспечивается `Cargo.lock`, который уже в репозитории.
Сеть в CI проверена и есть; для сборки без сети остаётся `cargo vendor`,
если это когда-нибудь потребуется.

## Последствия

- Формулировка «без зависимостей» в ADR-001 больше не верна дословно —
  здесь она уточнена.
- Появляется обязанность следить за зависимостями: их у ядра должно
  оставаться считаное число, и каждая — с записанной причиной.
- Сборка ядра требует либо сети, либо выкачанного кэша. Для CI это
  проверено, для офлайн-сборки дистрибутивов вопрос откладывается до M7,
  когда появится packaging.

## Открытые вопросы

- Нужен ли `cargo vendor` в репозитории ради офлайн-сборки пакетов
  дистрибутивов? Решать в M7 вместе с остальным packaging.
- Стоит ли ограничить глубину вложенности JSON явно. `serde_json` имеет
  защиту от переполнения стека, но лимит на глубину для нашего манифеста
  можно задать и жёстче.
