# Спайк 02 — мост Rust↔C++

Отвечает на вопросы [ADR-001](../../docs/adr/0001-rust-qt-bridge.md) и закрывает
формулировку критерия выхода M0 «главный FFI-риск снят».

## Что проверяется

1. Проходит ли событие путь адаптер → ядро → реакция → хост без Qt-типов в ядре.
2. Как асинхронное ядро отдаёт реакции в event loop Qt.
3. Переживает ли хост панику в Rust.
4. Во что обходится добавление одного нового варианта `DesktopEvent`.
5. Сколько стоит интеграция сборки и сколько кода придётся выбросить
   при смене подхода.

Проверяется **вариант A** из ADR-001: статическая Rust-библиотека, узкий C ABI,
безопасная C++-обёртка. Варианты B (cxx-qt) и C (оркестрация в C++) на этом
спайке не измерялись — см. раздел «Чего спайк не показал».

## Устройство

```text
core/
  Cargo.toml            # zero dependencies — сборка не требует сети
  include/openpet_core.h  # контракт границы, написан руками
  src/behavior.rs       # домен: приоритеты, cooldown, ttl. Ни C, ни Qt
  src/lib.rs            # слой FFI: перевод и защита от паники
host/
  corebridge.{h,cpp}    # владение, перевод Qt-типов, перенос в event loop
  main.cpp              # прогон проверок, годится для CI
```

Ядро — `QCoreApplication`, без GUI: спайк проверяет мост, а не отрисовку,
и поэтому запускается в CI без Wayland.

## Сборка и запуск

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo && cmake --build build && ./build/openpet-spike-bridge
```

Возвращает 0, если все проверки прошли. Тесты домена отдельно:

```bash
cd core && cargo test
```

## Результаты

Все проверки проходят, код возврата 0.

| Что проверено | Итог |
|---|---|
| Синхронный путь событие → реакция | ок |
| Приоритеты и cooldown работают через границу | ок |
| UTF-8 в `app_id` и `category` переживает границу | ок |
| Паника в Rust перехвачена, процесс жив, ядро продолжает отвечать | ок |
| Реакции из потока ядра приходят в главный поток Qt | ок |
| Сверка версии ABI при создании моста | ок |
| Тесты домена без FFI и без Qt | 3 из 3 |

### Стоимость сборки

| Действие | Время |
|---|---:|
| Холодная сборка целиком (Rust + Qt + линковка) | 3.95 с |
| Пересборка после правки Rust-домена | 0.59 с |
| Пересборка после правки C++-обёртки | 2.29 с |
| Пересборка после правки заголовка C ABI | 3.39 с |

Интеграция сборки — один `add_custom_command` с вызовом `cargo` и одна
`IMPORTED` библиотека. Corrosion и прочие посредники не понадобились.
Статическая библиотека ядра — 21 МиБ, итоговый исполняемый файл — 2.2 МиБ.

### Цена одного нового события

Измерено на добавлении `NotificationOccurred` с полем `category`
сквозь весь путь — 48 строк в 5 файлах:

| Файл | Строк | Что именно |
|---|---:|---|
| `core/include/openpet_core.h` | 6 | константа события, два поля строки, бамп версии ABI |
| `core/src/behavior.rs` | 7 | вариант перечисления и правило |
| `core/src/lib.rs` | 14 | зеркало полей и разбор строки |
| `host/corebridge.cpp` | 20 | метод-обёртка |
| `host/corebridge.h` | 1 | объявление |

Из них 20 строк в `corebridge.cpp` — механическое повторение одного и того же
шаблона: собрать POD, вызвать, перевести обратно. При восьми событиях это
терпимо, при тридцати потребует генерации.

Важнее числа другое: **добавление поля в структуру события ломает ABI**.
Раскладка меняется, и старый хост с новым ядром прочитает мусор. Поэтому
версия контракта поднимается вместе с полем, а хост сверяет её при создании
моста — эта проверка в спайке уже есть и срабатывает.

## Находки

**Домен действительно изолирован.** `behavior.rs` не знает ни о C, ни о Qt,
покрыт собственными тестами и не потребовал ни одной уступки ради FFI.
Это и есть проверяемое утверждение ADR-001.

**Перенос в event loop — три строки.** Callback приходит из потока ядра,
`QMetaObject::invokeMethod` с `Qt::QueuedConnection` переносит реакцию в поток
`CoreBridge`. Проверка в спайке сравнивает `QThread::currentThread()`
и подтверждает: все реакции получены в главном потоке.

**Паника перехватывается, но печатается.** `catch_unwind` на каждой границе
возвращает код ошибки вместо разворачивания стека в C++. При этом стандартный
хук паники всё равно пишет сообщение в stderr. Для продукта нужен свой хук:
во-первых, чтобы сообщение уходило в диагностический журнал, во-вторых, чтобы
в него не попало пользовательское содержимое (§9).

**`panic = "abort"` несовместим с этой схемой.** В профиле release он убил бы
`catch_unwind`, а вместе с ним — весь процесс хоста. Это зафиксировано
в `Cargo.toml` явно, с комментарием, потому что выглядит как безобидная
оптимизация размера.

**Плоская структура события вместо размеченного объединения.** Поля, не
относящиеся к текущему `kind`, игнорируются. Дороже по памяти на несколько
десятков байт на событие и заметно дешевле по сложности границы. Обязательное
условие — инициализация нулями на стороне хоста.

**Строки не пересекают границу во владение.** Наружу — фиксированный буфер
в 32 байта для ключа cooldown, внутрь — указатель с длиной, валидный только
на время вызова. Вопрос «кто освобождает» не возникает вовсе.

**Заголовок написан руками, а не сгенерирован.** cbindgen сгенерировал бы его
из `lib.rs`, но тогда изменение приватного типа в ядре молча меняло бы границу.
Заголовок и есть контракт, его изменения должны быть видны на ревью.

### Дважды пойманная собственная ошибка

Две проверки в спайке сначала падали, и оба раза виноват был не мост, а тест:
ожидалось три реакции от тикера, а приходило две, и ожидалось, что уведомление
даст реакцию, когда активен `low_battery` с приоритетом 70. В обоих случаях
ядро вело себя ровно по §FR-5.

Это стоит запомнить к M2: правила приоритетов и cooldown обманывают интуицию
при написании тестов, поэтому тесты поведения должны задавать время и начальное
состояние явно, а не полагаться на «сколько-то событий за столько-то миллисекунд».

## Чего спайк не показал

- Варианты B (cxx-qt) и C (оркестрация в C++) не измерялись. Вариант A
  выбирается по критериям ADR-001, а не по сравнению трёх реализаций:
  на такое сравнение ушла бы неделя вместо дня.
- Нагрузочного профиля нет: события подавались единицами, не тысячами.
  Стоимость границы на потоке событий проверяется в M3, когда появятся
  настоящие адаптеры.
- QML не участвует: реакция доходит до C++ и там останавливается. Путь
  до ViewModel закрывается в M1.
